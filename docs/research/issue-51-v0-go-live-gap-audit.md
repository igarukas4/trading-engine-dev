# Audit gap V0 untuk go-live

**Ticket:** [Audit V0 specification gaps that block safe go-live](https://github.com/igarukas4/trading-engine-dev/issues/51)  
**Tanggal audit:** 2026-09-16  
**Basis source:** `main` pada `a34b9143bc4f8ce4a1ae7176110a4868ee823532`; pemeriksaan VPS hanya read-only dari internet.

## Batas dan cara baca

Audit ini membandingkan source `main`, migrasi, spesifikasi V0 yang diterima, catatan deployment primer di repo, dan respons publik VPS. Ia tidak mengubah aplikasi, database, broker, connector, atau VPS.

`Absent` berarti tidak ada jalur implementasi yang ditemukan pada source yang diaudit. `Partial` berarti ada model atau schema, tetapi bukan perilaku produksi yang dipersyaratkan. `Unverified` berarti pemeriksaan dari luar VPS tidak cukup untuk membuktikan atau menyangkalnya.

Keputusan [Define evidence hierarchy and promotion gates for controlled LIVE and FULL_AUTO](https://github.com/igarukas4/trading-engine-dev/issues/50#issuecomment-5692907224) diperlakukan sebagai otoritatif: pemilik `BrokerAccount` bebas memilih LIVE unlock dan `MANUAL`/`SEMI_AUTO`/`FULL_AUTO` tanpa alasan, bukti minimum, soak period, atau limit jumlah akun. Inventory ini **bukan** daftar syarat promotion. Ia hanya mencatat interlock runtime dan kemampuan sistem yang harus benar-benar ada agar pilihan itu menghasilkan sistem yang fail-closed per akun.

## Bukti positif yang terverifikasi

- Deployment perimeter masih merespons: pada 2026-09-16, `https://trading.optitek.xyz/healthz` memberi HTTP 200 dengan verifikasi TLS sukses; `/` dan `/api/v1/system/status` memberi HTTP 401 tanpa kredensial. Ini membuktikan liveness publik dan Basic Auth perimeter, bukan kesehatan domain trading.
- Catatan primer repo, [`docs/operations/issue-48-acceptance.md`](../operations/issue-48-acceptance.md), merekam deploy shared-host yang lolos smoke pada 2026-09-15, termasuk health, penolakan forged header, dan reachability backend terautentikasi. Catatan yang sama menyatakan tidak ada `BrokerAccount` aktif atau operasi D2/D3 pada saat itu.
- GitHub Actions `Publish backend image` untuk commit audit `a34b914` sukses pada 2026-09-15 (run `34962640692`). Ini hanya membuktikan build/liveness image, bukan connector atau eksekusi broker.
- Schema migrasi sudah memodelkan banyak struktur yang diperlukan, misalnya `order_intents`, `outbox_events`, `connector_journal`, `fills`, dan `positions` pada [`backend/migrations/006_execution_safety.sql`](../../backend/migrations/006_execution_safety.sql). Namun source runtime belum memakai schema itu untuk domain execution.

## Kesenjangan VPS yang tidak boleh disimpulkan keliru

Pemeriksaan publik tidak memiliki akses ke Docker, PostgreSQL, release file, timer systemd, firewall provider, terminal MT5, atau connector Windows. Karena itu audit tidak menyatakan komponen tersebut tidak ada. Yang dapat dibuktikan dari source dan catatan adalah: deploy perimeter pernah sukses, tetapi service saat ini memang menyatakan `execution_available=false` dan `trading_enabled=false` di [`backend/app/main.py`](../../backend/app/main.py) 394-397 dan 509. Tidak ada bukti baru bahwa D2, connector, atau akun aktif kemudian terjadi.

## Urutan remediasi yang bergantung

1. **Control-plane custody dan schema/repository durability.** Implementasikan sole-custodian authentication/authorization dan audit durable; tambahkan command LIVE unlock/mode/lifecycle yang langsung dapat dipilih custodian sesuai tiket 50. Jangan menambahkan bukti, alasan, duration, atau approval gate. Tetapkan kontrak interlock per akun dan persist state/fence/epoch.
2. **Durable execution core.** Ganti store in-memory untuk account-operating state, market state, strategy/policy, signal/risk, execution, audit, dan dashboard event dengan repository PostgreSQL; buat transaksi PRE_ORDER/reservation/intent/outbox dan per-account ordered worker/recovery.
3. **Connector MT5 dan broker reconciliation.** Bangun connector Windows satu akun-satu session dengan identity/generation/lease, command journal, serialization, MT5-native protection proof, callback/idempotency, gap recovery, dan read-only broker reconciliation. Ini membuka fakta broker yang dibutuhkan langkah berikutnya.
4. **Interlock runtime.** Dari fakta durable/broker, jalankan last-mile risk, calendar adapter/blackout, stale/gap/UNKNOWN/protection quarantine, account-local overload, dan backup/alert/recovery health. Semua fault ini menutup exposure baru pada akun terdampak tanpa otomatis mengubah mode atau LIVE unlock, sesuai tiket 50.
5. **Emergency and recovery convergence.** Hubungkan close/reduce, global emergency, restart, takeover, UNKNOWN, dan protection repair ke account dispatch stream dan broker truth; buktikan netting/hedging serta multi-account isolation.
6. **Realtime UI and operations.** Baru kemudian buat snapshot/stream durable dan authenticated, command feedback/recovery UI, lalu operasional VPS: off-host encrypted backup, restore rehearsal, alert route, dan interlock health ingestion. Validasi keamanan/deployment dan use-case nyata menjadi observability setelah kemampuan runtime tersedia, bukan promotion prerequisite.

## Kesimpulan

Perimeter VPS dan image build ada, tetapi `main` masih foundation yang secara eksplisit menonaktifkan trading. Kesenjangan nomor 1-4 adalah jalur kritis menuju setiap bentuk eksekusi nyata; nomor 5-9 adalah interlock yang harus hidup ketika jalur itu dibuka. Tidak ada dasar teknis saat ini untuk menyatakan bahwa mode `FULL_AUTO` dapat mengirim atau merekonsiliasi order broker, terlepas dari kebebasan custodian untuk memilih mode tersebut.
